# Delegation Model v1 — субагенты и делегирование

Статус: **Draft**. Целевая модель расширяет существующий multi-agent runtime. Она не вводит второй оркестратор и не утверждает, что все механизмы уже реализованы.

## 1. Термины

- **General Agent** — постоянная идентичность главного агента, отвечающего за задачу и итоговый ответ.
- **Specialization** — выбранный профиль компетенций General Agent на конкретной фазе.
- **Subagent** — отдельный worker execution для ограниченного поручения, а не новая постоянная идентичность продукта.
- **Role** — функциональная ответственность worker: researcher, analyst, developer, tester, reviewer и т. п.
- **Delegation** — передача ограниченного поручения от Manager к worker с контрактом входа и результата.
- **Manager** — владелец декомпозиции, порядка, повторов, отмены, эскалации и итоговой приёмки.
- **Dispatcher** — предлагает план делегирования и распределение поручений; не выдаёт права и не принимает итоговую работу самостоятельно.

## 2. Интеграция с существующим runtime

Использовать текущие Agent Orchestrator, Coordinator/Project Agent, event transport, operation journal и существующие handoff/result schemas. Не создавать параллельный SubagentOrchestrator или отдельную систему разрешений.

Новые Playbook и Intelligence Library подключаются к существующему runtime через адаптеры и явные контракты. Миграция текущих схем не входит в этот документ.

## 3. Модель делегирования

1. General Agent / Manager получает задачу и критерии приёмки.
2. Playbook определяет фазы, требуемые компетенции и допустимые формы делегирования.
3. Dispatcher предлагает ограниченный граф поручений.
4. Manager проверяет граф: зависимости, параллелизм, бюджеты, контекст и допустимость каждого worker.
5. Для каждого поручения формируется Handoff Contract со ссылками на Task Context Package.
6. Worker выполняет только свой scope и возвращает Worker Result.
7. Runtime валидирует результат, evidence и статусы.
8. Manager принимает, отклоняет, уточняет или повторно делегирует работу.
9. General Agent формирует итоговый ответ, отделяя подтверждённые результаты от непроверенных выводов.

## 4. Контракт поручения

Существующие agent-handoff.v1 и worker-result.v1 остаются текущими контрактами обмена. Расширение вводится новой версией схемы, а не незаметным изменением v1.

Будущие поля:
- delegation_id и parent_delegation_id;
- execution_attempt_id и phase_id;
- objective и acceptance_criteria;
- specialization/role refs;
- playbook_ref и instruction_refs;
- task_context_package_ref;
- allowed_skill_refs и allowed_tool_operations;
- permission_scope_ref;
- dependency_ids;
- deadline, token/tool budget;
- output_schema_ref;
- cancellation_policy.

## 5. Ограничения графа

- Каждое поручение имеет одного родителя и явную цель.
- Граф ацикличен; worker не может самовольно расширять граф.
- Вложенное делегирование запрещено по умолчанию и включается только политикой Playbook.
- Ограничиваются глубина, fan-out, число циклов, длительность, токены и вызовы Tool.
- Параллельные workers получают изолированные контексты и области записи.
- Worker не может подтверждать собственный результат как окончательно принятый.
- Ошибка/timeout одного worker не превращается автоматически в успешный результат.

## 6. Контекст и полномочия

Worker получает минимальный Task Context Package: цель, критерии приёмки, необходимые выдержки, разрешённые документы и ссылки на доказательства.

Worker не получает автоматически всю историю диалога, полный репозиторий, все Skills, все Secrets или права родительского процесса.

Полномочия worker — пересечение прав сессии, родительского запуска, Playbook/Phase scope и worker policy. Worker не может расширить их через Role, Skill, prompt или handoff.

## 7. Приёмка результата

Manager проверяет:
- соответствие task/delegation/operation IDs;
- схему и обязательные поля результата;
- фактически прочитанные файлы и реально выполненные проверки;
- evidence references и происхождение утверждений;
- acceptance criteria;
- конфликтующие выводы других workers;
- ограничения покрытия и нерешённые вопросы.

Статус worker completed означает завершение поручения, но не принятие результата и не завершение родительской задачи.

## 8. Отмена и сбои

У каждого поручения есть operation ID, parent operation ID, deadline, terminal status и журнал событий. Отмена распространяется вниз по дереву согласно политике; уже совершённые внешние эффекты фиксируются отдельно. Повтор возможен только при безопасной retry policy.

## 9. Открытые вопросы

1. Сопоставить существующие AgentHandoff и WorkerResult runtime-типы с JSON Schema.
2. Проверить фактическое поведение Manager/Dispatcher и ограничение вложенного делегирования.
3. Определить, как текущий runtime передаёт project tools и scoped context.
4. Спроектировать v2 схемы только после тестов совместимости с v1.
5. Не менять рабочие handoff/result схемы в рамках навигационного рефакторинга.
