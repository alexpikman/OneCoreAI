# Execution Model v2

Статус: **Draft / архитектурный контракт**. Описывает целевой жизненный цикл; не подтверждает существующую реализацию.

## 1. Компоненты

| Компонент | Ответственность |
|---|---|
| Intent Resolver | Определяет Intent, оценку соответствия и альтернативы |
| Playbook Resolver | Находит совместимый Playbook и разрешает ссылки |
| Preflight Resolver | Проверяет потенциальные специализации, зависимости и политики |
| Registry | Предоставляет версионируемые сущности и связи |
| Playbook Engine | Управляет фазами, переходами, бюджетами и состоянием |
| Runtime Resolver | Выбирает специализацию для текущей фазы |
| Control Layer | Проверяет каждую операцию Tool до исполнения |
| Execution Engine | Выполняет разрешённую операцию |
| Decision Trace | Фиксирует решения, проверки, запросы и результаты |

Playbook Engine и Execution Engine — логически отдельные модули с явным контрактом; они не обязаны быть отдельными процессами.

## 2. Жизненный цикл

1. Принять задачу и доступный контекст.
2. Разрешить Intent; сохранить оценку соответствия и альтернативы.
3. Выбрать Playbook по критериям совместимости.
4. Выполнить Preflight: разрешить зависимости, проверить кандидатов, Skills, Tools, Schemas, политики и бюджеты.
5. Сформировать неизменяемый Execution Snapshot.
6. Перед каждой фазой выполнить Runtime Resolution.
7. Сформировать вход фазы и передать работу выбранной специализации.
8. Каждую операцию провести через Control Layer.
9. Проверить Outputs и условия перехода.
10. Зафиксировать Decision Trace и завершить запуск либо эскалировать.

## 3. Preflight

Каждый кандидат специализации обязан самостоятельно покрывать все обязательные компетенции фазы и иметь необходимые Skills, Tools и доступные операции. Нельзя объединять неполное покрытие нескольких кандидатов.

Preflight не выбирает фактическую специализацию для agent_choice или system_choice, если решение зависит от runtime-контекста или результатов предыдущих фаз.

## 4. Execution Snapshot

Snapshot закрепляет:
- ID и версию Playbook;
- версии фаз и связанных сущностей Registry;
- допустимые специализации и основания совместимости;
- версии Role, Skill, Tool и Capability Contract;
- версии Instruction и Schema;
- версии/идентификаторы Permission и Guardrail;
- модель и параметры, если они доступны и значимы;
- входной контекстный манифест и исходные бюджеты.

Snapshot фиксирует допустимое пространство, но не фактическую специализацию, которую Runtime Resolver выберет позже. Выбор записывается в Decision Trace со ссылкой на Snapshot.

## 5. Runtime Resolver

Перед каждой фазой он получает требования и актуальные входы, рассматривает только кандидатов Snapshot, проверяет актуальность ограничений, выбирает specialization по fixed/agent_choice/system_choice и записывает выбор с основаниями. Смена специализации не расширяет разрешённые операции и не ослабляет Guardrails.

## 6. Authorization, Guardrails и Confirmation

Authorization — проверка конкретной операции, аргументов и контекста:

is_authorized(operation, arguments, context) -> allow | deny

Эффективный доступ ограничивается GlobalPolicy, UserSessionRights, PlaybookRestrictions и ModeRestrictions. Политики задают ограничения на операции, ресурсы, аргументы и область действия; объединение должно иметь формальные правила сужения и deny-overrides.

Guardrail проверяется отдельно и может запретить операцию независимо от Authorization.

Confirmation — отдельное условие выполнения уже разрешённой операции. Ticket связывается с operation, канонизированным args hash и context hash, имеет срок действия и одноразовый статус. Отказ, timeout или отзыв не превращаются в разрешение. Отзыв не откатывает уже совершённый внешний эффект.

Неидемпотентность сама по себе не означает обязательное подтверждение. Оно определяется риском, эффектами, областью воздействия и Mode.

## 7. Control Layer

Перед каждой операцией Control Layer:
1. Разрешает Tool и версию Capability Contract из Snapshot.
2. Валидирует аргументы по Input Schema.
3. Проверяет ожидаемые эффекты.
4. Выполняет Authorization для конкретной операции и аргументов.
5. Проверяет Guardrails.
6. Проверяет требуемое Confirmation.
7. Применяет лимиты, дедупликацию и правила отмены.
8. Передаёт операцию Execution Engine.
9. Сверяет фактический результат и наблюдаемые эффекты с контрактом.
10. Записывает результат в Decision Trace.

Декларации Capability Contract недостаточно. Нужны реальные механизмы enforcement: файловая изоляция и проверка путей после symlink resolution, контроль запуска процессов, сетевые ограничения, ограничение доступа к секретам и аудит фактических операций.

## 8. Outputs и переходы

- Каждый обязательный Output валидируется по Schema.
- Отсутствие обязательного Output блокирует переход.
- exit_condition опциональна; если задана, должна быть истинна для нормального выхода.
- transitions проверяются сверху вниз; выбирается первый истинный.
- Отсутствие подходящего перехода приводит к определённому отказу или эскалации.

## 9. Отказы и отмена

Различать validation failure, authorization denial, guardrail denial, confirmation denied/timeout/revoked, tool timeout/failure, budget exceeded, cancellation и output validation failure.

Для каждого терминального состояния задать остановку фазы, безопасную очистку, фиксацию фактических эффектов, состояние Artifact и дальнейшую эскалацию. Повтор допустим только при проверенной retry policy и безопасной семантике операции.

## 10. Открытые вопросы

1. Формализовать алгебру Authorization для операций, областей, аргументов и deny-overrides.
2. Утвердить риск-модель Confirmation.
3. Определить компенсационные операции; reversible=true без compensation contract недостаточно.
4. Выбрать и протестировать enforcement filesystem/process/network/secret access.
5. Уточнить отзыв политик во время активного Snapshot.
6. Определить точный формат Snapshot и миграцию версий.

До закрытия вопросов разрешён только ограниченный read-only прототип без заявлений о полноценной безопасности.
